## 1. Vocabulary

- **Rollout id** (`rollout_id`). The driver's loop index. Each iteration consumes one rollout batch of `--rollout-batch-size` prompt groups and runs `--num-steps-per-rollout` optimizer steps on it.
- **Weight version**. The integer rank 0 stamps on every engine at the end of a sync with `update_weight_version` (`miles/backends/training_utils/weight_update/session.py:86-92`, called at `updater.py:165`). The driver then publishes it to the `RolloutExecutor` (`miles/ray/placement_group.py:321-322`, `miles/ray/rollout/rollout_executor.py:378-386`). What it counts depends on the backend:
  - **Megatron**: successful optimizer steps. The count lives in a `weight_version` parameter of the model companion (`miles/backends/training_utils/model_companion.py:26`), is bumped after each successful `optimizer.step()` (`miles/backends/megatron_utils/model.py:659-662`), and is checkpointed with the model. `update_weights` reads it and hands it to the updater (`miles/backends/megatron_utils/actor.py:949-950`). A fresh run publishes `0` at the initial sync, and each rollout advances the version by the number of optimizer steps it took.
  - **Torch-native backends (FSDP, torchtitan)**: a sync counter that starts at `0` and increments on every sync that runs (`miles/backends/training_utils/torch_native/actor.py:295-297`), so the first training data carries version `1`.

  Both drivers sync once before the first rollout (`train.py:48`, `train_async.py:41`). The `disk-delta` protocol's first sync only captures a baseline: `begin_sync` returns `False` (`protocols/delta.py:119-127`), and engines with no version yet are stamped `"0"` (`delta.py:256`, `:458-472`). `disk-delta` also refuses to resume from a training checkpoint (`miles/utils/arguments.py:3837-3842`).
- **Staleness**. Measured in weight versions: `current_version - oldest output-span version` of a group, where `current_version` is the version the driver last published (`miles/rollout/filter_hub/common_filters.py:21-24`, `:104-105`). Data generated by the weights now on the engines has staleness `0`; open-instruct's `training_step - model_step` counts the same data as `1`. On Megatron one version is one optimizer step. On torch-native backends it is one sync. Prompt-KV versions are not part of it (3.1).

## 2. Execution modes

Miles has two single-policy drivers, `train.py` and `train_async.py`, and three rollout functions that matter here. The standard `InferenceRolloutFn` generates one batch on demand and aborts the leftovers. `FullyAsyncRolloutFn` keeps a persistent background producer. The `random_async` example keeps a background producer thread of its own. (`train_multi_policy.py` runs one generate → train → sync loop per policy, `train_multi_policy.py:110-160`, and is not traced here.)

| Mode | Entry | Colocate | Overlap | Staleness |
|---|---|---|---|---|
| Sync | `train.py` | Yes or no | None | 0, plus partial-rollout carry-over |
| One-step async | `train_async.py` | No (`train_async.py:24`) | Generation N+1 overlaps training N | Exactly one sync for interval 1 |
| Fully async | `train_async.py --fully-async` | Yes, with limits (`miles/utils/arguments.py:102-121`) | Continuous generation, paused during training under `--colocate` | Variable. Bounded only by `--max-weight-staleness` |
| Random async (example) | `train_async.py` + custom rollout fn | No | Continuous (own thread) | Variable, unfiltered |

The timelines below use Megatron versions with one optimizer step per rollout, so `U→v1` publishes the step count after `T0`.

### 2.1 `train.py`, not colocated

In each iteration the loop generates, trains, and then updates the weights. The call sequence is `prepare_rollout` → `rollout_executor.get` → `actor_model.train` → `update_weights` (`train.py:103-156`):

```
version:   v0                     v1                     v2
engines :  [G0 ~~~~~~~~]          [G1 ~~~~~~~~]          [G2 ~~~
trainer :              [T0][U→v1]             [T1][U→v2]
```

`G_N` is generated entirely under the weights that `T_{N-1}` produced, so the batch is on-policy up to the train/inference numerical mismatch. At the end of the batch, `abort()` sends `/abort_request {"abort_all": true}` to every worker (`miles/rollout/inference_rollout/inference_rollout_train.py:27-66`, called at `:183`). This clears the over-sampled groups still in flight, so no request is running when `U` happens.

`train.py` never reads `--update-weights-interval`. It syncs after every rollout except the last, and after the last one only when an eval is due (`train.py:141-156`). The interval flag only affects `train_async.py:88`, `train_multi_policy.py:152`, the `keep_old_actor` bookkeeping (see section 4.4), and the frozen-version guard (`miles/utils/weight_version.py:17-18`).

### 2.2 `train.py`, colocated (`--colocate`)

Training and rollout take turns on the same GPUs. `--colocate` turns on `--offload-train` and `--offload-rollout` unless you pass `--no-offload-train` or `--no-offload-rollout` (`miles/utils/arguments.py:3844-3848`). The handoff inside one iteration (`train.py:104-156`) runs as follows:

```
G_N on engines → release engine memory (cuda_graph [+kv_cache] [+weights] per --offload-rollout-level)
             → onload trainer, T_N
             → offload trainer (sleep) or clear_memory
             → resume engine weights memory → U (CUDA-IPC) → resume kv_cache + cuda_graph
```

With `--colocate-memory-peak-device gpu` (`arguments.py:442-455`), the order changes so that both copies briefly coexist on the GPU instead of in host RAM: offload KV → onload trainer → offload engine weights (`train.py:108-111`). After training it runs clear_memory → onload engine weights → offload trainer (`train.py:144-149`). The timeline is the sync one from 2.1, with offload and onload stages between the phases.

### 2.3 `train_async.py` (one-step overlap)

The loop starts generating the next batch before it trains on the current one. When a sync is due it waits for that next batch to finish before touching the weights (`train_async.py:133-137`, comment: *"sync generate before update weights to prevent update weight in the middle of generation"*).

```
version:   v0                             v1                     v2
engines :  [G0 ~~~][G1 ~~~~~~~~~~~~]      [G2 ~~~~~~~~~~~]       [G3 ~~~
trainer :          [T0 on G0]  wait G1 [U→v1][T1 on G1] wait G2 [U→v2][T2 on G2]
```

1. `G_{N+1}` is launched with `eager_create_task` at `train_async.py:102`, before `T_N` at `:104-114`.
2. At `:133-138` the driver awaits `G_{N+1}`, then runs `U`. No generation is in flight during the sync, so `--pause-generation-mode` does not matter here.
3. At `:84-85` the next iteration uses the batch it already awaited.

With interval 1, `T_N` trains on data from the weights *before* `T_{N-1}`. Every token is exactly one sync stale: one version on torch-native backends, `--num-steps-per-rollout` versions on Megatron. A larger interval makes the lag vary within the interval: with interval 2, `G2` is generated under the initial weights but trained by `T2`, after both `T0` and `T1` have stepped.

### 2.4 `train_async.py --fully-async`

`--fully-async` swaps the rollout function for `FullyAsyncRolloutFn` (`arguments.py:62-73`). It rejects `--partial-rollout`, `--pause-generation-mode abort`, `--recompute-logprobs-via-prefill`, `--rollout-all-samples-process-path`, a separate `--rollout-function-path`, multi-LoRA, and the legacy rollout API (`arguments.py:92-132`). The same fn also serves eval unless you pass `--eval-function-path` (`arguments.py:71-72`).

The first `get()` asserts that a weight version has been published, then starts one persistent producer task on the rollout event loop (`miles/rollout/fully_async_rollout.py:104-118`). From then on it runs this loop (`fully_async_rollout.py:174-185`):

```
while True:
    wait until not paused-for-eval
    while scheduler.has_capacity(pending_groups, group_budget): submit one prompt group
    wait for progress (a group finished, or with sample granularity a sample finished)
    for each finished group: await buffer.put(group)      # blocks when the buffer is full
```

The in-flight budget is `rollout_batch_size` groups, or `--async-max-concurrent-samples // n_samples_per_prompt` groups when that flag is set (`fully_async_rollout.py:149-153`). A trainer step only *drains* `rollout_batch_size` finished groups from the buffer (`fully_async_rollout.py:208-256`).

```
version :  v0                   v1                   v2
producer:  ==G==G====G===G==|pause|===G==G===G====|pause|==G==...   (never idle except in U / eval)
buffer  :     ↑  ↑    ↑   ↑        ↑  ↑   ↑             ↑
trainer :  [D0][T0 on D0]  [U→v1][D1][T1 on D1]  [U→v2][D2][T2]
```

When a sync is due, the next drain is deferred until after `U` (`train_async.py:92`, `:139-140`). That drain is called with `input.weight_version` = the new version, which the buffer's staleness filter compares against. When no sync is due (interval > 1), the next drain starts before training (`train_async.py:101-102`). `U` itself runs in the middle of generation: the engines pause, receive the weights, and resume.

`D` usually takes milliseconds when the buffer is non-empty. The wall time per step moves from `rollout + train` toward `max(rollout, train)` (`fully_async_rollout.py:1-7`).

**With `--colocate`.** This combination rejects the FSDP backend, `in_place`, and rollout fault tolerance, and needs interval 1 when engine weights are offloaded (`arguments.py:102-121`). Generation does not overlap training here. After each drain the driver pauses the engines with `--pause-generation-mode`, flushes the cache, and offloads KV and weights (`train_async.py:93-98`). It then trains, offloads the trainer, onloads the engine weights, and syncs (`:129-138`). The sync skips its own pause and resume because the driver owns them (`arguments.py:76-77`, `weight_update/session.py:21-22`, `:30-31`). Finally it onloads KV, resumes generation, and starts the next drain (`train_async.py:141-146`). Requests in flight are retracted for the whole train window and re-prefilled under the new weights.

### 2.5 Random async (`examples/infra_features/random_async/`)

This example is a stress test with random tokens and random rewards. It runs its own `threading.Thread` with a private asyncio loop and a `queue.Queue(maxsize=1000)` (`random_async_rollout.py:274-354`). The rollout function drains `rollout_batch_size` groups from that queue (`:386-424`). The launcher runs `train_async.py` **without** `--fully-async` (`run_random_async_3node.py:177`, and no `--fully-async` anywhere in that file), so the driver takes the one-step branch (2.3). It waits for the next drain before each `U`, while the thread keeps generating across `U`.

```
producer thread: =====================(continuous)==========|pause|=========...
trainer        : [D0][T0 ‖ D1 ][wait D1][U→v1][T1 ‖ D2][wait D2][U→v2]
```

Because generation always spans `U`, the example is useful for exercising `--pause-generation-mode in_place|retract` and the p2p/broadcast paths. It has no staleness filter, no buffer capacity other than the 1000-group queue, and no metrics from `DefaultDataBuffer`. Its submit loop also adds at most one group per second (`random_async_rollout.py:320-330`, a `break` plus `asyncio.sleep(1)`), so it ramps up slowly. The README titles it "Random fully-async example", but it is not `--fully-async`.

### 2.6 The submission scheduler (`--rollout-submission-granularity`)

`miles/rollout/submission_scheduler.py` decides when a finished unit frees a submission slot. Groups are always submitted whole.

- `group` (`submission_scheduler.py:16-28`): a slot frees when the whole group task returns. This is the default for `InferenceRolloutFn` (`inference_rollout_train.py:120`).
- `sample` (`submission_scheduler.py:31-63`): every finished sample decrements `samples_in_flight` through a done-callback that fires on success, exception, or cancel (`inference_rollout_common.py:167-169`). A new group goes out when `samples_in_flight + group_size <= budget * group_size`. This is the default under fully async (`fully_async_rollout.py:81`). In agentic runs it keeps the engines busy while straggler trajectories finish.

The scheduler only paces submission. It does not change which policy version generated anything.

## 3. Staleness: where it comes from and how it is bounded

### 3.1 Version stamping is per token span

Each generate call appends one `WeightVersionsPerCall` to `sample.weight_versions` (`miles/utils/types.py:185`, `:503`). It is built from SGLang's `meta_info` by `WeightVersionsPerCall.from_meta_info` (`types.py:95-122`):

- If `meta_info["weight_versions"]` exists, it holds a list of `{version, start, end}` over the output tokens. Each entry becomes an absolute-position `WeightVersionSpan`. This is how the engine reports that a weight update landed *inside* one request.
- Otherwise the single `meta_info["weight_version"]` is attributed to every output token of the call. SGLang fills that field when the response returns, so a request that straddled an update would be attributed entirely to the newer version, which under-counts span. This fallback only matters for engines without span support.
- The engine emits the span list on a finished or aborted request. This was checked against the SGLang 0.5.21 release; the Miles image builds the `sglang-miles` branch (`docker/Dockerfile:18`, currently 0.5.22.dev), so SGLang line numbers are approximate there. When `/update_weight_version` changes the version, the scheduler records `(old_version, len(output_ids))` on every live request. That covers the running batch, the last batch, the waiting queue (where retracted requests sit) and the chunked request (`python/sglang/srt/managers/scheduler.py:5410-5445`, `python/sglang/srt/utils/weight_versions.py:39-50`). When the request finishes, the scheduler turns those events into contiguous spans (`managers/scheduler_components/output_streamer.py:516-525`, `weight_versions.py:66-84`). The TokenizerManager then writes both `weight_versions` and `weight_version` into `meta_info` (`managers/tokenizer_manager.py:2424-2432`, `weight_versions.py:90-107`). Aborted requests get the same spans through `_make_abort_req` (`scheduler.py:6114-6125`). So `generation_version_span` can be trusted. A request that is still held in the TokenizerManager when the version changes (see 3.3) has no tokens yet, so every one of its tokens is correctly attributed to the new version.
- **Prompt-KV versions.** Output spans say nothing about the KV the prompt attends over, which can come from the radix cache or from a prefill under older weights (3.3). With `--sglang-enable-prefill-weight-versions`, the engine also returns `meta_info["prefill_weight_versions"]`: spans over the prompt tokens naming the version whose KV each token used. They become `WeightVersionsPerCall.prefill_spans` (`types.py:139-149`), and `prefill_lag` is the call's newest output version minus its oldest prompt-KV version (`types.py:83-89`). With the flag on, every call with a prompt must report them (`miles/utils/weight_version.py:42-53`). They feed the `rollout/weight_version/prefill_*` metrics (section 7) but not the staleness filter. The flag and its engine side exist only in the `sglang-miles` build, so the engine behaviour was not checked here.
- Anchoring requires `return_logprob=True`, and the code asserts this (`types.py:99-108`).

`assert_samples_weight_version_sane` rejects any output or prompt-KV span stamped `"default"` (an engine that never received a sync) or any non-numeric span (`miles/utils/weight_version.py:33-66`, called at `rollout_executor.py:316`). `assert_weight_version_is_published` fails the run if the driver stops publishing versions (`weight_version.py:17-30`, called at `rollout_executor.py:199-203`).

### 3.2 Can one trajectory span weight updates?

Yes, in four ways:

1. **Fully async / random async, mid-request.** `U` pauses in-flight requests and resumes them (see 3.3). Tokens sampled before the pause carry `v` and tokens sampled after carry the new version, even within one generate call, and a multi-turn trajectory can cross several updates. In `retract` mode the context the post-update tokens attend over is recomputed under the new weights. In `in_place` mode it is not (3.3). The metrics `rollout/fully_async/avg_generation_version_span` and `rollout/weight_version/mixed_version_ratio` (`miles/ray/rollout/metrics.py:117-121`, `:199-215`) measure this.
2. **Partial rollout (sync or one-step drivers).** With `--partial-rollout`, `abort()` collects the unfinished samples, with their partial `tokens`, `rollout_log_probs`, and `weight_versions` (`inference_rollout_train.py:46-66`), and returns them to the data source (`inference_rollout_common.py:234-235`). The flag switches the data source to `LegacyRolloutDataSourceWithBuffer` (`arguments.py:4377-4380`), which serves buffered samples first (`miles/rollout/data_source.py:151-163`), and the next rollout appends to them under the new weights (`miles/rollout/generate_hub/single_turn.py:25-33`). `sample.metadata["start_rollout_id"]` records where the trajectory began. `--mask-offpolicy-in-partial-rollout` (loss-mask the old prefix) works only on the legacy path. The class-based path raises (`arguments.py:86-90`).
3. **Multi-turn agents under fully async.** Each turn is a separate call with its own version.
4. **External agents / session server.** Same stamping, via `session/samples/merge.py:154`.

`reset_for_retry` (`types.py:445-472`) clears `weight_versions` and `rollout_log_probs` when a prompt is recycled under `--async-unused-samples-handler retry`, so a retried group restarts from scratch at the current version. It also sets `status = ABORTED` (`types.py:465`) rather than `PENDING`, so a custom generate function must set its own final status. I did not trace every generate function to confirm they all do.

### 3.3 In-flight requests at weight update (`--pause-generation-mode`)

The engine-side behaviour below was checked against the SGLang 0.5.21 release (see 3.1). SGLang paths are relative to `python/sglang/srt/`.

Rank 0 runs the session frame: pause, flush (unless `in_place`), `begin_weight_update`, the transfer, `end_weight_update`, `update_weight_version`, resume (`session.py:15-32`, `updater.py:123-169`). The transfer RPCs go out with `flush_cache=False` (`sglang_api_client.py:132`, `:384`, and neither `protocols/broadcast.py` nor `protocols/cuda_ipc.py` overrides it). SGLang's `begin_weight_update` and `end_weight_update` do not flush either (`managers/scheduler_components/weight_updater.py:290-317`). So the explicit `/flush_cache` in `maybe_pause_engines` is the only cache flush in a sync. Miles sends `/update_weight_version` with `abort_all_requests=False` (`sglang_api_client.py:435-439`). SGLang defaults that field to `True` (`managers/io_struct.py:2058`), so a custom caller that omits it aborts every request.

| Mode | What SGLang does | Cache flushed? | Consequence for tokens |
|---|---|---|---|
| `retract` (default) | The TokenizerManager sets `is_pause` and forwards the request to the scheduler (`managers/tokenizer_manager.py:2140-2144`). The scheduler sets `_engine_paused`, so its event loop stops scheduling batches (`managers/scheduler.py:5591`, `:1914`, `:1958`). It collects every unfinished request in the running batch, the last extend batch and the chunked prefill, and frees their KV **without** inserting it into the radix tree (`scheduler.py:5603-5657`, `managers/schedule_batch.py:2268`). They go back to the waiting queue with `output_ids` and output log-probs intact (`schedule_batch.py:1961-2010`). After resume they are re-prefilled over `origin_input_ids + output_ids` (`schedule_batch.py:1572-1579`) | Yes. The flush succeeds because a paused scheduler leaves the waiting queue out of its idle check (`scheduler.py:5187-5189`) | Already-sampled tokens keep the log-probs they were sampled with and are stamped `v`. The whole prefix, prompt and old tokens alike, is recomputed under the new weights, so later tokens are clean new-version samples. No stale KV survives |
| `in_place` | Same pause flag, then the scheduler returns at once, leaving the running batch, the chunked prefill and their KV untouched (`scheduler.py:5593-5601`). After resume, decoding continues on the existing KV | No (`session.py:25-26`). SGLang would refuse anyway, because a flush needs an empty running batch (`scheduler.py:5019-5020`, `managers/io_struct.py:1835-1836`) | New tokens are stamped with the new version but attend over KV computed with `v`. The radix cache is not flushed either, so **any later request whose prefix hits the cache** also reuses `v` KV: group siblings, the next turn of a multi-turn agent, and waiting requests not yet prefilled. Output stamps record neither effect; prompt-KV spans do (3.1). Under `--fully-async` this mode turns on `--namespaced-radix-cache` by default (`arguments.py:3990-3998`): every request carries an `extra_key` naming the rollout call its sample started under (`miles/rollout/base_types.py:58-74`, `generate_utils/generate_endpoint_utils.py:88-89`). Under fully async that is the drain current when the group was submitted (`fully_async_rollout.py:107`, `:157`). A later call cannot reuse an earlier call's prefix; reuse within one call remains |
| `abort` | Not forwarded to the scheduler. The TokenizerManager sets `is_pause` and keeps sending `abort_all` until no generate call holds `model_update_lock` (`tokenizer_manager.py:2145-2153`) | Yes | Requests return `finish_reason=abort` with their partial output and spans, which sets `Sample.Status.ABORTED` (`types.py:508-509`). The whole group is filtered. Fully async rejects this mode (`arguments.py:123-126`) |

**Requests sent during a pause wait. They are not rejected.** Every generate call waits on `is_pause_cond` before it tokenizes and dispatches (`tokenizer_manager.py:894-895`), and `continue_generation` clears the flag and wakes them (`tokenizer_manager.py:2155-2159`). This holds in all three modes. The fully-async producer is **not** paused during `U`. It keeps submitting up to its in-flight budget, and those requests wait in the TokenizerManager until resume. The producer is only paused for shared-engine eval (`fully_async_rollout.py:134-145`).

**The sync never waits for requests to drain.** Weight-update RPCs skip `model_update_lock` while the engine is paused (`managers/tokenizer_control_mixin.py:466-478`, `:512-520`). An unpaused update takes the writer lock, which waits for every in-flight generate call to return, because each call holds the reader lock for its whole lifetime (`tokenizer_manager.py:897`). Miles always pauses first.

Engine-side caveats:

- `--fully-async --colocate`: the driver pauses with `--pause-generation-mode` and flushes before training (`train_async.py:93-98`), and the session skips its own pause and resume (2.4). `in_place` is rejected there (`arguments.py:106-109`).
- `disk-delta` combined with `in_place` and requests in flight. The protocol pauses and skips its own flush (`protocols/delta.py:400-405`), but `update_weights_from_disk` defaults to `flush_cache=True` (`managers/io_struct.py:1889`). The scheduler asserts that the flush after the load succeeds (`managers/scheduler_components/weight_updater.py:117-122`, `:143`), and with a non-empty running batch it cannot. This combination should therefore fail at the first sync that has requests in flight. That conclusion comes from reading the code, not from a run.
- PD disaggregation, prefill side. A retract pause keeps a live mid-chunk prefill request rather than retracting it, so its prefix KV stays on the old weights (`scheduler.py:5659-5666`, a TODO in the source).
- `--use-session-server --use-rollout-routing-replay` with `retract` logs a warning that retract-mode R3 has known SGLang issues (`arguments.py:3488-3494`).

Under the one-step and sync drivers no request is in flight at `U` (sections 2.1 and 2.3), so the mode only matters for fully async, random async, and anything else that drives the engines outside the driver's rhythm.

### 3.4 Bounds per mode

| Mode | Bound | Mechanism |
|---|---|---|
| Sync | 0, except partial-rollout carry-over (unbounded in principle: a sample aborted repeatedly keeps its oldest prefix) | Abort at the end of each batch |
| One-step | One sync (interval 1) | The driver awaits `G_{N+1}` before `U` |
| Fully async | None by default | `--max-weight-staleness` (default `None`, `arguments.py:921-931`) |
| Random async | None | None |

With `--max-weight-staleness S`, every pass of `DefaultDataBuffer.get()` first sweeps the whole buffer. It computes `current_version - oldest output-span version` for each group (`fully_async_data_buffer.py:244-258`, `common_filters.py:104-105`) and hands any group with staleness greater than `S` to the unused handler: `drop` (the default) discards it, and `retry` recycles its prompts (`fully_async_rollout.py:84-86`, `:258-264`). It then pops the oldest `rollout_batch_size` groups, FIFO (`fully_async_data_buffer.py:234-236`). Prompt-KV versions are ignored, as the flag's help says (`arguments.py:925-926`).

Three things bound staleness indirectly:

- **Buffer capacity.** `int(--async-data-buffer-capacity-factor × rollout_batch_size)` finished groups, `2.0` by default; the factor must be at least `1.0` (`fully_async_data_buffer.py:157-162`). A full buffer blocks `put()` (`:184-188`), which blocks the producer loop, so no new submissions go out.
- **The in-flight cap** (2.4).
- **FIFO consumption.** At `B` groups per step, a finished group waits at most about `capacity / B` steps.

None of these limits how long a single straggler can stay *in flight*. Its oldest span can be many versions old when it finishes, which is why the filter uses the *oldest* span.

### 3.5 What happens to unused work

| Where | What | Fate |
|---|---|---|
| Fully async `put` | Any sample `ABORTED` (for example an agent timeout, a sandbox crash, or a cancelled group task, `fully_async_rollout.py:187-198`) | Unused handler (drop/retry). Counted in `aborted_groups_filtered` (`fully_async_data_buffer.py:190-195`) |
| Fully async `put` | Missing reward, or rejected by `--dynamic-sampling-filter-path` | Always dropped. Counted as `rollout/dynamic_filter/drop_<reason>` (`:197-212`) |
| Fully async `get` | Staleness greater than `S` | Unused handler. Counted in `stale_groups_filtered` (`:244-254`) |
| Sync or one-step end of batch | Over-sampled groups still in flight | Aborted. Recycled only with `--partial-rollout` |

## 4. Off-policy correction: what is the "old" policy?

### 4.1 Three log-prob sources

For each response token `t`:

- `logπ_rollout(t)` comes from `sample.rollout_log_probs`, which SGLang returned while sampling. It belongs to whichever version generated that span, so it is the behavior policy up to the kernel mismatch.
- `logπ_old(t)` is the trainer's forward-only pass at the *start* of the train step. It uses the `actor` weights, or the `old_actor` weights with `--keep-old-actor` (`miles/backends/megatron_utils/actor.py:720-737`). It runs unless `--use-rollout-logprobs` is set without `--get-mismatch-metrics`, or unless `--skip-actor-forward-only` is set.
- `logπ_θ(t)` comes from the training forward, with gradient.

`policy_loss_function` picks the ratio denominator (`miles/backends/training_utils/loss/hub/losses.py:97-141`):

```
old_log_probs = rollout_log_probs         if --use-rollout-logprobs
              = trainer log_probs         otherwise        (or detached logπ_θ under --skip-actor-forward-only)
ppo_kl        = old_log_probs - logπ_θ                                  (losses.py:186-189)
r_t           = exp(-ppo_kl)
pg_loss_t     = max(-r_t·A_t, -clip(r_t, 1-eps_clip, 1+eps_clip_high)·A_t)   (math_utils.py:253-277)
                [dual-clip with --eps-clip-c for A_t<0]
```

### 4.2 What the ratio anchors to, per mode

Let `k` be the trainer's current version and `k-s` the behavior version:

| Flags | Ratio denominator | Staleness corrected? | Train/inference mismatch corrected? |
|---|---|---|---|
| Defaults | `π_k` (trainer recompute) | **No.** The clip is centred on `π_k`, a policy that never generated the data | No |
| `--use-rollout-logprobs` | `π_rollout ≈ π_{k-s}` | Yes, inside the clip (the trust region is around the behavior policy) | Folded in, uncorrected |
| `--use-tis` | `π_k`, and the loss is multiplied by `w = clamp(π_k/π_rollout)` | Yes, as a truncated IS weight outside the clip (decoupled PPO) | Yes, the same weight |
| `--keep-old-actor` | `π_old_actor` (see 4.4) | Only where `old_actor` = the behavior weights | No |

`--use-rollout-logprobs` and `--use-tis` are mutually exclusive (`arguments.py:3681-3682`). In sync mode `s = 0`, so these flags only address the kernel mismatch. In one-step mode `s` is one sync. In fully async `s` varies per token span, and the IS weight is per token, so mixed-version trajectories are handled token by token when using rollout log-probs.

`validate_async_off_policy_correction` (`arguments.py:4255-4273`, called at `train_async.py:25` and by the multi-policy validation, `miles/utils/multi_policy/utils.py:147`) requires one of the three flags, but it **returns immediately when `--use-critic` is off** (`:4265-4266`). GRPO or REINFORCE runs under `train_async.py` therefore start with the default "anchor to `π_k`" row and no warning. The function's docstring describes exactly this hazard.

### 4.3 The correction functions

The built-in TIS is `vanilla_tis_function` (`loss/hub/corrections.py:7-32`), applied at `losses.py:234-283`:

```
ρ_t        = exp(logπ_old(t) - logπ_rollout(t))
w_t        = clamp(ρ_t, --tis-clip-low (default 0), --tis-clip (default 2.0))
pg_loss_t ← w_t · pg_loss_t
metrics    : tis = mean ρ_t,  tis_clipfrac = mean[w_t ≠ ρ_t],  tis_abs = mean |ρ_t − 1|,  ois = mean r_t
```

Here "old" is the trainer recompute, so `ρ` covers staleness plus kernel mismatch, and the PPO ratio `r = π_θ/π_old` covers the within-step drift over multiple minibatches.

- **`icepop_function`** (`corrections.py:35-62`) sets `w_t = ρ_t` when `ρ_t ∈ [low, high]` and `0` otherwise. Tokens outside the band are dropped instead of truncated. Select it with `--custom-tis-function-path miles.backends.training_utils.loss.hub.corrections.icepop_function`.
- **MIS** (`examples/infra_features/train_infer_mismatch_helper/mis.py:151-310`) adds token, sequence, or geometric levels and truncate, clip, or mask modes, rejection sampling (`rs_*`), a veto threshold, and batch normalization. It reads extra args (`tis_mode`, `tis_level`, `rs_*`) from its YAML. A custom function can return modified loss masks (rejection sampling), and on Megatron the denominators stay the pre-rejection `rollout_mask_sums` (`losses.py:267-277`); the torch-native backends do not ship `rollout_mask_sums`, so there the rejected tokens also leave the denominator. See [Train-infer mismatch helper](/examples/infra-features/train-infer-mismatch-helper).
- **OPSM** (`--use-opsm`, `--opsm-delta`; `loss/hub/math_utils.py:183-221`) zeroes a whole sequence when `A < 0` and `mean_t(logπ_old − logπ_θ) > δ`. It uses whichever `old_log_probs` the flags selected.
- **ESS ratio** (`losses.py:290-301`, logged as `train/ess_ratio`) is computed from `exp(-ppo_kl)`.

`--get-mismatch-metrics` requires `--custom-tis-function-path` (`arguments.py:3684-3687`), even though the built-in TIS function exists.

The mismatch diagnostics `train_rollout_logprob_abs_diff` and `train_rollout_kl` (a k3 estimate of KL(rollout‖train)) are emitted whenever rollout log-probs are present (`losses.py:344-368`). They compare a trainer-scored policy with `π_rollout`: the `π_old` recompute, or the detached training forward when no recompute ran, even under `--use-rollout-logprobs`. So **in async modes they measure staleness plus kernel mismatch**, not kernel mismatch alone. To separate the two, compare them with a sync baseline.

### 4.4 `--keep-old-actor`

This flag is Megatron-only. It keeps extra CPU copies of the weights (`actor.py:432-437`) and rotates them at every sync (`actor.py:956-965`):

- With interval 1: `old_actor ← rollout_actor` (the weights the engines had), then `rollout_actor ← actor` (the weights just sent).
- With interval > 1: `old_actor ← actor` (the weights just sent).

At the next train step, `compute_log_prob` runs on `old_actor` (`actor.py:720`). Tracing the one-step loop in 2.3 shows that this is exactly the behavior policy for **`train_async.py` without `--fully-async` and with interval 1**:

- `T_N` trains on `G_N`, which was generated by the weights synced before `T_{N-1}`.
- That is what `old_actor` holds after the rotation.

Elsewhere it is not exact:

- **`train.py`**: `G_N` comes from the *newest* weights, but `old_actor` is one sync behind them.
- **One-step with interval > 1**: the first batch after each sync was generated before it.
- **Fully async**: only groups generated entirely between the previous sync and the latest one match.

`--keep-old-actor` is incompatible with `--skip-actor-forward-only` (`arguments.py:4199`) and with `--rematerialize-param-from-master-weight` (`arguments.py:3287`).

## 5. Weight-sync mechanics

### 5.1 Driver-side sequence

```
update_weights(args, actor_model, rollout_executor, inference_controller)   placement_group.py:296-322
├─ inference_controller.start_update_weights()     @acquires_lock    inference_controller.py:232-252
│     pause health checkers; wait until every cell is PendingWeights|Serving;
│     snapshot (engines, gpu counts/offsets, cell→workers_hash)
├─ TrainerController.update_weights(info)                            ray/train/group.py:391-400
│  └─ retry(_execute_first_alive("update_weights", info), 30 attempts)
│        └─ MegatronTrainRayActor.update_weights                     megatron_utils/actor.py:917-972
│             reconnect if any cell's workers_hash changed (new/healed engines)   :931-936
│             v = companion weight_version; WeightUpdater.update_weights(v)       :949-950
│             [ci] compare engine version; rotate keep_old_actor copies           :953-965
├─ on exception: inference_controller.abort_update_weights()  @releases_lock      placement_group.py:309-313
├─ inference_controller.end_update_weights()       @releases_lock    inference_controller.py:258-269
│     snapshotted PendingWeights cells, workers_hash unchanged → register with router → Serving
└─ rollout_executor.set_weight_version(v)
```

The controller's context lock is held from `start_update_weights` to `end_update_weights` or `abort_update_weights`. That serializes weight syncs against offload, onload, pause, resume, eval preparation, cell reconciliation, and fault injection. A sync that raises after all 30 attempts releases the lock through `abort_update_weights`.

### 5.2 The session frame (`updater.py:123-169`)

```
begin_sync(v)              protocol hook; False → skip round (disk-delta baseline)
rank 0: pause_generation(mode) [+ flush_cache unless in_place]   session.py:15-26 (driver's job under --fully-async --colocate)
rank 0: register LoRA adapters; begin_weight_update(selector, sync_base)
gloo barrier
for bucket in hf_weight_iterator.iter_hf_weights(...):   every rank joins the TP/EP/PP gathers;
    if sender: protocol.send_bucket(bucket)              only senders materialize and send
protocol.after_base_weights(); gloo barrier
protocol.finalize(v)
rank 0: end_weight_update(checksums) → update_weight_version(v) → continue_generation
gloo barrier; protocol.after_engines_resumed()
```

The caller supplies `v` (section 1); the updater no longer keeps a counter of its own. The whole frame is synchronous on the driver. `train_async.py:138` awaits it, so **no training happens during a sync in any mode**. Only rollout (fully async without `--colocate`) or the tail of the next batch (one-step, before `U`) overlaps with training.

Protocols that set `use_weight_update_session = False` skip the pause, begin, end, and version calls and run their own frame. Only `disk-delta` does this (`protocols/delta.py:78-81`).

**Bucketing.** `iter_hf_weights` converts Megatron shards to HF names, keeps "atomic update groups" together, and packs units greedily into buckets of at most `--update-weight-buffer-size` bytes (512 MiB by default; `hf_weight_iterator/__init__.py:94-120`, `bucketing.py:70-86`). A unit is never split. The Megatron gather batches use the same limit (`megatron_utils/update_weight/hf_weight_iterator_direct.py:240-252`). The torch-native backends (FSDP, torchtitan) drive the same `WeightUpdater` with their own HF iterators (`training_utils/torch_native/actor.py:92-104`).

### 5.3 Protocols

`get_weight_transfer_protocol` (`weight_update/protocol.py:73-95`) picks CUDA-IPC whenever `--colocate` is set. Otherwise `--update-weight-transfer-mode` decides.

| Protocol | File | Sender(s) | Transport | Notes |
|---|---|---|---|---|
| `broadcast` (default), `broadcast_packed` | `protocols/broadcast.py` | Replica rank 0 per PP shard (`:58-69`) | Per-shard NCCL group `miles-pp_{pp}` = sender + every engine GPU (`:86-131`) | Per bucket: an HTTP `update_weights_from_distributed` with names, dtypes, and shapes to every engine, then the broadcasts, then a wait for all engines (`:146-188`). `broadcast` sends one async `dist.broadcast` per tensor. `broadcast_packed` flattens the bucket into one byte broadcast and requires Megatron without `--colocate` (`:157-166`, `:191-208`, `protocol.py:77-78`). With PP > 1, a world ticket lock serializes the PP stages' broadcasts to avoid an engine-side NCCL deadlock (`:33-40`, `:71-83`) |
| CUDA-IPC (colocate) | `protocols/cuda_ipc.py` | Every rank covered by an engine | Each rank serializes its bucket as a `FlattenedTensorBucket` of CUDA-IPC handles, `gather_object`s it to the engine group's source rank, which calls `update_weights_from_tensor` (`:170-194`, `:201-258`) | `gather_pp=True`, so PP is gathered first. Engines beyond the actor GPUs in a hybrid layout get a NCCL broadcast tail (`:98-119`). Calls `torch.cuda.ipc_collect()` after resume (`:196-198`) |
| `p2p` | `protocols/p2p.py` | Trainer ranks assigned an (engine, engine rank) target; every target gets exactly one sender, spread over the data replicas (`protocols/utils/rollout_engine_rank_assignment.py:22-84`) | Mooncake RDMA writes from two pinned-CPU transfer buffers, each loaded through a `ModelReplica` shaped like the target shard (`p2p.py:122-139`) | A `ModelParamStager` holds tensors until every HF input of a parameter group has arrived (`p2p.py:125`). `after_base_weights` waits for all writes (`:94-100`). A write that fails or is still running after `--p2p-transfer-timeout` fails the update (`protocols/utils/transfer_buffers.py:61-90`) |
| `disk-delta` | `protocols/delta.py` | Replica rank 0 | Shared FS: xor or overwrite byte deltas against a CPU snapshot, zstd, per-tensor checksum (`:129-144`, `:291-312`, `:340-377`) | Engines `/pull_weights` **before** the pause, so the pull overlaps generation. Then pause, `update_weights_from_disk` (which stamps the version), and continue (`:379-421`). See [Disaggregated RL Rollout](/advanced/disaggregated-rollout) |

### 5.4 What each side does during a sync

- **Trainer**: all ranks sit in the gather collectives. Senders also move bytes. Rank 0 drives the engine RPCs. Nothing trains. With `--offload-train` and the actor asleep, process groups are rebuilt and later destroyed around the sync (`actor.py:927-929`, `:969-970`). The weights come from the live GPU model, or from the CPU backup when colocated, asleep, or switched to another model tag (`actor.py:898-910`).
- **Engines**: paused. The retract, in-place, or abort semantics from 3.3 apply. New requests wait in each engine's TokenizerManager until resume (3.3). The weight RPCs themselves never flush the cache, because Miles sends them with `flush_cache=False` (3.3). When the session ends, SGLang re-finalizes the weights (`end_weight_update`, `python/sglang/srt/managers/scheduler_components/weight_updater.py:304-317`), records the version stamp on live requests, and resumes. Under `--fully-async --colocate` the driver has already paused them and offloaded their KV (2.4).
- **Fault-tolerance health checks** are paused from `start_update_weights` until the next `prepare_rollout` or `prepare_eval` (`inference_controller.py:235`, `:150-157`). A check that was in flight when the pause began is discarded (`ft_utils/health_checker.py:196-201`).
- **Timing** is logged as `perf/update_weights_time` (the `@timer` on `actor.update_weights`), `perf/update_weights_implementation_time`, and `perf/finalize_and_resume_engines_time` (`updater.py:145`, `:161`). Timers accumulate in the trainer process and are flushed when the *next* `train()` logs (`miles/backends/training_utils/metrics/perf.py:21-23`, called via `actor.py:809-813`), so a sync's time shows up one step late. The same applies to the protocol metrics `perf/update_weights_density` and `perf/update_weights_wire_bytes` from disk-delta (`delta.py:423-443`, drained at `actor.py:812`).

## 6. Fault tolerance and async

The current machinery is cells plus health checkers plus the mini FT controller. [Fault Tolerance](/advanced/fault-tolerance) describes an earlier stack: `rollout_manager.py`, `health_monitor.py`, and `recover_updatable_engines` no longer exist.

- **Detection.** `--use-fault-tolerance` with `rollout` in `--ft-components` (the default component, `arguments.py:3254-3261`) gives each rollout cell a `SimpleHealthChecker` that calls `/health_generate` (`miles/ray/rollout/server_cell.py:306-321`). After `--rollout-health-check-failure-threshold` consecutive failures (each bounded by `--rollout-health-check-timeout`, spaced by `--rollout-health-check-interval`), the cell reports `Healthy=False` (`ft_utils/health_checker.py:217-226`). `--fully-async --colocate` refuses rollout fault tolerance (`arguments.py:117-121`).
- **Healing.** The mini FT controller polls `/api/v1/cells` and suspends and then resumes an unhealthy cell, with backoff (`ft_utils/mini_ft_controller.py:169-237`). A replacement cell goes Initializing → **PendingWeights** (`server_cell.py:176-209`). It joins the router only at the end of the next weight sync (`inference_controller.py:258-269`, `server_cell.py:211-214`), which guarantees it never serves version `"default"`. Under fully async a healed engine therefore sits idle until the next `U`, and the sync reconnects to it (NCCL group or P2P plan rebuilt) because its `workers_hash` changed (`actor.py:931-936`).
- **In-flight requests to a dying engine.** `post()` retries up to 60 times with 1 s sleeps (`miles/utils/http_utils.py:219-251`, `:417-428`). Each retry is a fresh request through the router, so that turn restarts on another engine. If every retry fails, the exception propagates out of `generate_and_rm_group`, which cancels the sibling samples first (`inference_rollout_common.py:172-180`). In the fully-async producer, `_collect_group_result` re-raises it (`fully_async_rollout.py:187-189`), which ends the worker; `_on_worker_error` cancels the waiting drain (`:202-206`), and later drains fail the `worker has ended` assert (`:212`). Only a cancelled group task is converted to an aborted group (`:190-198`). An agent integration that catches its own errors and sets `ABORTED` gets the softer path (3.5). In the sync or one-step `InferenceRolloutFn`, a failed group task is logged and skipped (`inference_rollout_train.py:140-144`).
- **Engine death during a sync.** The broadcast or IPC collective blocks until NCCL times out (`--distributed-timeout-minutes`, reset to 10 at `arguments.py:458`). `TrainerController.update_weights` retries on the next alive *trainer* cell with the same engine snapshot `info` (`group.py:391-400`). The code marks weight-update fault tolerance as work in progress (`inference_controller.py:91-99`, "TEMPORARY … reverted with the weight-update fault tolerance work"), so treat recovery from a mid-sync engine loss as unsupported.
- **P2P.** A write that fails or outlives `--p2p-transfer-timeout` raises (`transfer_buffers.py:74-89`). There is no fallback to broadcast.

These are the async-health signals, with the names as logged:

| Metric | Source | Read it as |
|---|---|---|
| `rollout/fully_async/queue_size` | `fully_async_data_buffer.py:287-328` | Pinned at 0: rollout-bound. Pinned at capacity: train-bound, and staleness grows |
| `rollout/fully_async/{avg,max}_staleness` | Same | Oldest-span lag of the groups that were trained on |
| `rollout/fully_async/{avg,max}_post_generation_staleness` | Same | Lag of the newest span. It measures time spent in the buffer after finishing |

| `rollout/fully_async/stale_groups_filtered`, `aborted_groups_filtered` | Same | Wasted generation |

| `rollout/fully_async/buffer_{avg,max}_staleness` | Same | Age of what is still waiting |
| `rollout/weight_version/{mean,median,max,min}`, `rollout/weight_version/mixed_version_ratio` | `ray/rollout/metrics.py:117-121`, `:199-215` | Every mode. The oldest version per sample and the fraction of samples with more than one version |

| `train/ppo_kl`, `train/pg_clipfrac`, `train/ess_ratio` | `losses.py:370-377` | Drift within a step against the chosen denominator |
| `train/train_rollout_logprob_abs_diff`, `train/train_rollout_kl` | `losses.py:344-368` | Trainer-scored policy vs `π_rollout`: staleness plus mismatch in async modes |
| `train/tis`, `train/tis_clipfrac`, `train/tis_abs`, `train/ois` | `corrections.py:26-30`, `losses.py:387-394` | A rising `tis_clipfrac` or `tis_abs` means the IS weights are saturating |
| `train/opsm_clipfrac` | `losses.py:396-397` | Masked negative-advantage sequences |
| `perf/train_wait_time`, `perf/wait_time_ratio` | `metrics/perf.py:50-54` | Trainer idle between steps. This includes the sync, the drain, and, in one-step mode, the wait for `G_{N+1}` |
| `perf/rollout_time` | `ray/rollout/metrics.py:273-277` | Under fully async this is **drain** time, not generation time |
| `perf/update_weights_time` and sub-timers | 5.4 | Sync cost, logged one step late |

Failure modes to watch for:

1. **Silent anchoring to `π_k`.** Running GRPO under `train_async.py` without `--use-rollout-logprobs` or `--use-tis` (4.2). Every token is at least one sync off-policy and nothing corrects for it. `train_rollout_kl` is large compared with a sync run.
2. **A staleness blow-up hidden by the filter default.** With `--max-weight-staleness` unset, a slow trainer lets `buffer_max_staleness` climb without limit. With it set and `drop`, look for `stale_groups_filtered` approaching `rollout_batch_size`: the trainer is starved and the drain logs `No completed rollout groups for 30.0s` (`fully_async_data_buffer.py:226`). On Megatron the threshold counts optimizer steps, so it must grow with `--num-steps-per-rollout` and `--update-weights-interval`.
3. **Stragglers crossing many updates.** High `max_generation_version_span` means individual agent trajectories run across many syncs. Combined with `in_place`, the post-update tokens also attend over stale KV, and so does every later request in the same rollout call that hits a radix-cache prefix computed before the update (3.3); `prefill_lag_max` measures it when prompt-KV versions are on. Prefer `retract` if correctness matters more than recompute cost.
4. **The fully-async producer died.** An exception in a group other than cancellation ends the producer and fails the waiting drain (6). Check the rollout logs for the first traceback (`fully-async rollout worker ended`), not the drain error.
5. **Mixed-version eval on shared engines.** Eval points should show `eval/{ds}/weight_version/mixed_version_ratio == 0`. See [Fully Async RL: Metrics](/user-guide/fully-async#metrics).
6. **Frozen version.** `assert_weight_version_is_published` fires after `max(3, interval+1)` rollouts without a publish (`weight_version.py:14-30`). This usually means a custom driver skipped `update_weights`.

## 10. Stale claims elsewhere, and surprises

These existing docs and help strings disagree with the code:

- **`docs/advanced/fault-tolerance.md`** describes a stack that has been removed (`rollout_manager.py`, `health_monitor.py`, `recover_updatable_engines`, and a p2p path under `megatron_utils/update_weight/update_weight_from_distributed/`). The page flags itself as outdated. The current flow is described in section 6.
- **`docs/advanced/p2p-weight-transfer.md`** places the shared pipeline in `miles/backends/megatron_utils/update_weight/` "via `common.py`". The protocols now live in `miles/backends/training_utils/weight_update/`, the Megatron directory only holds the HF iterators, and there is no `common.py`. It also says the engines "increment their weight version". In fact rank 0 sets the version by RPC (`session.py:86-92`).
- **`docs/user-guide/fully-async.md`** says one version "normally corresponds to one optimizer step" only with `--update-weights-interval 1`. On Megatron a version is one successful optimizer step whatever the interval (`megatron_utils/model.py:659-662`); one sync advances it by every step taken since the last sync.
- **`--fully-async` help** (`arguments.py:709-711`) says eval "keeps the standard rollout function". `resolve_rollout_function_paths` routes eval to `FullyAsyncRolloutFn` unless you pass `--eval-function-path` (`arguments.py:62-73`), and the module docstring agrees with the code.
- **`--max-weight-staleness` help** (`arguments.py:925-929`) says stale groups are "recycled back to the data buffer". They go to `--async-unused-samples-handler`, which defaults to `drop`.
- **The random-async README** calls itself "fully-async", but the launcher does not pass `--fully-async` (2.5).

These are behaviours worth knowing:

1. `train.py` ignores `--update-weights-interval` (2.1).
2. The async off-policy guard only applies to PPO with a critic (4.2).
3. `--keep-old-actor` matches the behavior policy only for one-step async with interval 1 (4.4).
4. Weight-sync timings and disk-delta metrics are logged one step late (5.4).
5. No mode overlaps training with the weight sync itself (5.2).
6. A healed rollout engine idles until the next sync (6).
7. `reset_for_retry` leaves `status = ABORTED` (3.2).
8. On Megatron a weight version is an optimizer step, not a sync, so `--max-weight-staleness` and every staleness metric scale with `--num-steps-per-rollout` and `--update-weights-interval` (1).
